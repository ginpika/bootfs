# 动态 mononode 组网

动态模式实现用户确认的部署语义：独立运行的节点发现彼此并组建一个集群，新的独立节点可随时加入；主动下线先调整共识成员；突然失去多数成员时暂停权威读写。加入/退出不重分布已有对象。冲突数据保留为递增版本，不以覆盖或“最后写入者胜出”丢弃原资源。

这是新增的 `bootfs.metadata.mode=dynamic` 路径。旧 `embedded` 和静态 `raft` 模式仍可运行，但不能把有数据的目录就地改成另一种模式。请先用 [内核备份恢复](mononode-backup.md) 建立一个新 seed。

## 启动与一键连接

每个节点使用独立根目录，配置可被其他节点访问的 HTTP 入口，以及相同的显式配对密钥。节点 ID、集群 ID、活动存储代和通信地址会持久保存，不需要预先定义 group-id 或 peers。

```sh
export BOOTFS_CLUSTER_TOKEN='replace-with-a-long-shared-random-token'
java -jar target/bootfs-v1.0.0-beta.1.jar \
  --spring.profiles.active=dev \
  --tfs.root-path=/absolute/new/node-a \
  --tfs.web-entrypoint=http://127.0.0.1:8181 \
  --bootfs.metadata.mode=dynamic
```

本机启动第二个节点时修改根目录、`--server.port=8182` 和 HTTP 入口。Raft 端口首次默认选择可用端口并持久保存；需要固定防火墙/容器映射时显式设置 `--bootfs.cluster.raft-address=host:port` 并暴露对应 TCP 端口。HTTP 入口和节点 ID 当前不允许在已有根目录中随意更改。

跨机器将 HTTP 入口改为私网地址，并显式设置 `--bootfs.raft.allow-insecure-network=true`。当前尚无 Raft mTLS，应使用受保护的私网/隧道承载。配对 token 认证 HTTP 控制和对象传输，不能替代加密。

动态模式默认启用局域网发现。签名组播使用 UDP 55929、239.192.42.66，TTL=1；显式加入可用的 IPv4 组播接口和本机环回接口，避免系统默认路由选错接口；密钥本身不广播，过期或签名不符的公告不会改变成员。只有使用同一配对密钥的节点会连接。两个独立节点使用确定顺序选择目标，避免互相同时合并；已建立集群即使只剩一个成员，也保持原身份。

发现接口不可用不会阻止节点启动；`status.discoveryAvailable` 表示本机发现传输是否已开启。组播不可达时打开管理菜单中的“节点组网与版本”（`/cluster.html`），输入任一目标成员的 HTTP 地址并点击“连接”。可用 `--bootfs.cluster.discovery.enabled=false` 关闭自动连接，只通过该页面操作。

HTTP 管理接口也可用于自动化（启用 SSO 时需要登录会话或配对 token）：

```sh
curl -H "X-BootFS-Cluster-Token: $BOOTFS_CLUSTER_TOKEN" \
  -H 'Content-Type: application/json' -d '{"url":"http://127.0.0.1:8181"}' \
  http://127.0.0.1:8182/api/cluster/connect
```

返回 202 表示持久连接任务已建立，**不代表合并已完成**。`GET /api/cluster/status` 显示 `FROZEN → ATTACHING → ACTIVE`；待完成时普通业务入口返回 503，防止从旧独立历史继续提供权威服务。失败原因保留在状态中，后台继续重试。不要删状态文件或旧存储代强行恢复独立写入。

## 带数据合并与版本

连接前检查原始对象及待发布内容存在且符合已有长度/摘要。等待 k 副本的未完成上传及漫画组装意图一并迁入；它们保持原耐久策略，在加入后利用集群节点继续完成，避免“等待副本导致无法组网”的循环。旧协议的未完成副本接收须先恢复完成。先持久冻结独立节点的写入，再将原始元数据提交到目标集群。合并使用多键条件批次，目标并发写入导致条件失败时重新计算；成功结果按 mergeId 持久保存，丢失响应重试不会重复增加版本。

- 无冲突的 key 和资源直接并入共享权威状态。自定义 KV 也保留；冲突的普通元数据 key 通过 `namespace=metadata` 保存原始字符串版本。旧共识身份和迁移标记不作为新集群身份导入；已有异步副本重试任务随资源身份迁入，继续完成原来的复制意图。
- 冲突 S3 key 的原绑定是版本 n，新节点绑定是 n+1；第三个独立来源继续增加版本。默认 key 指向新绑定，旧 UUID 内容仍可读取。
- 相同 UUID 来自两个独立历史时，新来源获得确定的新不可变 UUID；对应库存、路由、文档和父子/副本引用一起改写。新节点只在本地复制这些冲突内容及媒体文件，原文件和原共识目录保留，不发生跨节点对象重分布。冲突资源版本列出两份 UUID。
- 元数据和版本历史先合并（连接任务完成前，新引用的对象可能暂时不可达），随后新成员以空共识副本加入，接收目标集群的快照/日志；本地库存追上后才恢复业务入口。

在组网页面可查阅 S3 或资源版本，或者使用：

```text
GET /api/cluster/versions?namespace=s3&key=/s3/bootfs/path/to/object
GET /api/cluster/versions?namespace=resource&key=原始UUID
```

记录包含 version、来源和完整原始 value，其中 UUID 可经 `/f/{uuid}` 读取。当前实现的是**组网冲突版本保留**，尚不是完整 S3 Versioning API，也不表示所有普通 PUT/标签编辑都会产生版本。S3 后续覆盖不会自动回收被冲突历史引用的资源；显式按 UUID 删除资源仍遵循统一墓碑生命周期。

## 主动下线、重启和故障

页面“安全下线本节点”对应 `POST /api/cluster/leave`。先由剩余成员提交移除，再关闭本节点共识服务；不会搬走该节点已有的对象。下线期间页面仍可查看状态；重启进程后重新加入原集群。最后一个成员可以停止服务，其持久历史保留以便重启。

直接杀进程、拔网线或停机属于突然失联，不自动缩减投票集合。剩余多数成员继续读写；失去多数时权威操作失败，不能通过本地超时把隔离分区升级成新集群。两个投票成员中突然失去一个就没有多数；若希望维护时只保留一个可写成员，应在关闭另一个之前安全退出。

被显式移除的失联节点重启时，会探测已知存活成员；若确认本节点已不在成员集中，使用新的空共识代重新申请加入，不复用旧投票状态。整组同时重启且没有成员确认移除时，继续恢复原持久日志，不凭联系失败另建集群。

存活多数可通过 `POST /api/cluster/remove`（`{"nodeId":"..."}`）移除已失联成员；仍必须由有效共识确认，不能强制绕过多数。切勿把“发现不到”直接当成“可以删除成员”。

没有 re-balance 也意味着：某对象所有耐久副本所在的节点都离线时，对象暂时不可读。元数据多数派不能产生缺失的对象字节。副本策略见 [内核说明](mononode-kernel.md)。

## 实际边界

当前支持独立节点加入一个现有集群；不自动合并两个已经建立的多成员集群，也不将退役集群的外节点库存冒充本机完整库存。局域网发现、一次性全量元数据合并和固定位置对象路由是第一代实现；多网卡/容器组播、生产网络分区/掉电、长时间压力仍需独立环境验证。

动态成员使用 Apache Ratis 的成员变更协议，配置变更比较先前配置，防止并发连接相互删掉新成员。单成员向双成员扩展显式开启 Ratis majority-add；在变更未确认或突然失联时保留不确定状态并等待原多数恢复，不做强制重建。原理及限制参考 [Ratis 成员变更说明](https://apache.googlesource.com/ratis/+/7214931166164c8207947dfa916c2e499e4d7b0e/ratis-docs/src/site/markdown/membership-change.md)。
